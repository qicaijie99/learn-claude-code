对，你这个判断是对的：**当前代码没有硬性确保后台任务完成通知不会被 compact 掉。**

更准确地说：

> **正在运行中的后台任务状态不会被 compact 掉，因为它存在 `background_tasks/background_results` 这些内存表里，不靠 messages 保存；但“已经注入到 messages 里的完成通知”会像普通消息一样参与 compact，不能保证长期保留。**

## 1. 当前代码里哪些东西会被 compact 影响？

你的 `agent_loop()` 每轮开头都会执行三层预处理：

```python
message[:] = tool_result_budget(message)
message[:] = snip_compact(message)
message[:] = micro_compact(message)
```

如果上下文还是太大，还会：

```python
message[:] = compact_history(message)
```

也就是说，`message` 里的历史内容确实会被压缩、裁剪、替换。

后台完成通知的注入方式是普通 text block：

```python
message.append({
    "role": "user",
    "content": [
        {"type": "text", "text": n}
        for n in bg_notifications
    ]
})
```

所以它不是特殊的 `tool_result`，也不是单独的持久状态，**进入 `message` 后就会被当作普通 user message 处理**。

---

## 2. 哪些 compact 会影响它？

### `micro_compact`

`micro_compact()` 主要处理旧的 `tool_result` block。后台完成通知是：

```python
{"type": "text", "text": "<task_notification>...</task_notification>"}
```

所以它一般不会被 `micro_compact()` 直接替换掉。

---

### `snip_compact`

`snip_compact()` 会裁掉中间消息，只保留头部和尾部。后台完成通知如果落在“中间旧消息”区域，就可能被替换成：

```text
[snipped N messages]
```

这时模型就看不到那个 `<task_notification>` 了。

---

### `compact_history`

`compact_history()` 更危险。它会把整个 messages 写 transcript，然后用 LLM 总结，最后替换成一条 summary message：

```python
return [{"role": "user", "content": f"[Compacted]\n\n{summary}"}]
```

这意味着 `<task_notification>` 是否保留，完全取决于总结模型有没有把它总结进去。代码里保存 transcript，但实际继续对话只保留 summary。

---

### `reactive_compact`

`reactive_compact()` 会保留最近尾部 5 条左右，其余部分总结。如果后台通知在最近尾部，大概率还在；如果已经比较旧，就会进入 summary，也不保证保留完整 `bg_id/command/summary`。

---

## 3. 所以现在的真实状态是这样

```mermaid
flowchart TD
    A["后台任务启动"] --> B["立刻生成占位 tool_result<br/>Background task bg_0001 started"]
    B --> C["background_tasks 记录 running"]
    C --> D["后台线程完成"]
    D --> E["background_results 保存完整 output"]
    E --> F["collect_background_results()"]
    F --> G["生成 task_notification text"]
    G --> H["append 到 messages"]
    H --> I{"后续发生 compact?"}
    I -- "否" --> J["LLM 可直接看到通知"]
    I -- "是" --> K["通知可能被 snip / summarize"]
    K --> L["LLM 只能依赖 summary<br/>不保证还能对应 bg_0001"]
```

关键区别：

```text
未完成时：
background_tasks/background_results 在内存里，不靠 messages，不会被 compact 影响。

完成并 collect 后：
background_tasks/background_results 被 pop 掉，结果变成 messages 里的 text notification。
这之后就可能被 compact 影响。
```

你的 `collect_background_results()` 里完成任务会被 `pop` 出 `background_tasks` 和 `background_results`，然后生成 `<task_notification>` 字符串。

## 4. 这是不是严重问题？

要看目标。

如果你的目标只是教学版：

```text
后台任务完成后，尽快通知下一轮 LLM。
```

现在可以接受。

如果你的目标是更稳的工程版：

```text
后台任务结果必须可追踪、可恢复、可被后续引用。
```

那现在不够稳。

原因是：

```text
1. 完整 output 只保存在内存 background_results 里。
2. collect 后立刻 pop，内存表里也没了。
3. 注入 messages 的只有 summary，最多 200 字。
4. 这个 summary 后续还可能被 compact 掉。
5. 如果用户晚点问“刚才 bg_0001 结果是什么”，不一定能答准。
```

## 5. 更稳的改法：后台结果要持久化 + 进入 context

建议设计成：

```text
后台任务完成
    ↓
完整结果写入 .task_outputs/background/bg_0001.txt
    ↓
background_tasks 表中保留 completed 状态和 result_path
    ↓
collect_background_results 只注入通知，但不删除任务记录
    ↓
update_context 每轮注入 pending/completed background task index
    ↓
用户要完整结果时，通过 read_file 或 get_background_result 工具读取
```

这样即使 messages compact 了，状态仍然在 context 或磁盘里。

## 6. 可以这样改数据结构

现在你的结构大概是：

```python
background_tasks: dict[str, dict] = {}
background_results: dict[str, str] = {}
```

可以改成：

```python
BACKGROUND_DIR = WORKDIR / ".task_outputs" / "background"

background_tasks[bg_id] = {
    "tool_use_id": block.id,
    "command": cmd,
    "status": "running",
    "result_path": None,
    "notified": False,
    "created_at": time.time(),
    "completed_at": None,
}
```

后台完成时：

```python
def worker():
    result = execute_tool(block)

    BACKGROUND_DIR.mkdir(parents=True, exist_ok=True)
    result_path = BACKGROUND_DIR / f"{bg_id}.txt"
    result_path.write_text(result, encoding="utf-8", errors="replace")

    with background_lock:
        background_tasks[bg_id]["status"] = "completed"
        background_tasks[bg_id]["completed_at"] = time.time()
        background_tasks[bg_id]["result_path"] = str(result_path)
```

这样完整结果不靠 `messages` 保存。

## 7. `collect_background_results()` 不要 pop 掉记录

现在完成后你会：

```python
task = background_tasks.pop(bg_id)
output = background_results.pop(bg_id, "")
```

工程上建议改成：

```python
def collect_background_results() -> list[str]:
    notifications = []

    with background_lock:
        ready_items = [
            (bg_id, task)
            for bg_id, task in background_tasks.items()
            if task["status"] == "completed" and not task.get("notified")
        ]

        for bg_id, task in ready_items:
            task["notified"] = True
            notifications.append(
                f"<task_notification>\n"
                f"  <task_id>{bg_id}</task_id>\n"
                f"  <status>completed</status>\n"
                f"  <command>{task['command']}</command>\n"
                f"  <result_path>{task['result_path']}</result_path>\n"
                f"</task_notification>"
            )

    return notifications
```

这样做的好处：

```text
通知可以被 compact 掉，但 background_tasks 里仍然知道 bg_0001 完成了。
完整结果在 result_path。
```

## 8. 再把 background task index 注入 context

你的 `update_context()` 现在只注入工具、workspace、skills、memory 等，不包含后台任务索引。

可以加一个：

```python
def background_status_context() -> str:
    with background_lock:
        if not background_tasks:
            return ""

        lines = ["Background tasks:"]
        for bg_id, task in sorted(background_tasks.items()):
            line = (
                f"- {bg_id}: {task['status']}, "
                f"command={task['command']!r}"
            )
            if task.get("result_path"):
                line += f", result_path={task['result_path']}"
            lines.append(line)

        return "\n".join(lines)
```

然后：

```python
def update_context(context: dict, messages: list) -> dict:
    ...
    return {
        "enabled_tools": list(TOOL_HANDLERS.keys()),
        "workspace": str(WORKDIR),
        "skills": list_skills(),
        "memory_index": memory_index,
        "memories": relevant_memories,
        "background_tasks": background_status_context(),

```

`assemble_system_prompt()` 里也加：

```python
background = context.get("background_tasks", "")
if background:
    sections.append(background)
```

这样即使 `<task_notification>` 被 compact 掉，LLM 仍然能在 system prompt 里看到：


## 9. 最理想：加一个 `get_background_result` 工具

再加一个工具：

```python
def run_get_background_result(task_id: str) -> str:
    with background_lock:
        task = background_tasks.get(task_id)

    if not task:
        return f"Error: background task {task_id} not found"

    result_path = task.get("result_path")
    if not result_path:
        return f"Task {task_id} is {task['status']}; no result yet"

    try:
        return Path(result_path).read_text(encoding="utf-8", errors="replace")[:50000]
    except Exception as e:
        return f"Error reading result: {e}"
```

然后注册：

```python
TOOLS.append({
    "name": "get_background_result",
    "description": "Read the saved result of a background task by task_id.",
    "input_schema": {
        "type": "object",
        "properties": {
            "task_id": {"type": "string"}
        },
        "required": ["task_id"]
    }
})

TOOL_HANDLERS["get_background_result"] = run_get_background_result
```

这样后续用户问：

```text
刚才 bg_0001 的完整输出是什么？
```

模型就不用依赖旧 messages，直接调用工具读结果。

## 10. 结论

你说得对：

> **当前没有确保后台完成通知不会被 compact 掉。**

当前机制只是：

```text
启动时：用 tool_result 占位，保证 tool_use 协议完整。
完成时：用 task_notification 普通文本通知 LLM。
后续：这个通知可能被 compact。
```

更稳的工程设计应该是：

```text
messages 只负责通知
background_tasks/context 负责状态
磁盘 result_path 负责完整结果
get_background_result 工具负责按需读取
```

一句话概括：

> **不要把后台任务结果的可靠性建立在 messages 不被 compact 上；应该把后台任务做成独立状态系统，messages 只是提示 LLM“有结果了”。**
